- C vs E is a definitional judgement. I chose C because the obstacle is that the materials hold and can produce no number the paper reports (no 2XWT value in the paper; production trajectory not deposited), not a compute or dependency limit. An auditor reading E as "the paper-level analysis (re-running 200-400 ns MD) exceeds compute" could reasonably pick E; even then, a re-run would have no paper value to compare with.
- The PROTOCOL class scheme has no "no reproducible target" category; any class assigned here describes the deposit, not the correctness of the paper's own 5DK3/6UMT numbers, which this audit did not examine.
- I did not check whether the 2XWT production trajectory or the 5DK3/6UMT data exist in other ThermoPCD Dataverse datasets; the audit scope is this one dataset.
- The deposited SD/SEM in FINAL_RESULTS_MMPBSA.dat are population (ddof=0) values; PREREG step 1 names ddof=1. Only the averages are pre-registered targets, so this does not change any check result; both SDs are in outputs/internal_checks.json.
- R_a-R_c have no paper value to compare with, so same_direction_and_significance_as_paper is null; the pre-registered checks define no hypothesis test, so p_value is null (descriptive one-sample t p-values are in outputs/robustness.json).
- The 400 ns RMSD series (2xwt-rs3-400ns-310k-rmsd.xvg) starts at about 4.48 nm at t=0, while the 200 ns series starts near 0; it was computed against md_1_30.tpr, which is twice the size of md_0_10.tpr. The cause cannot be checked without the trajectory; recorded descriptively, not as a bug (outputs/xvg2csv_check.json first_data_row).
- The optional AmberTools GB recompute used AmberTools 26 on aarch64 (authors: Amber 21 sander, x86_64) and an mdin edit to restore extdiel=78.5 (diffs/README.md); it checks the deposited intermediates, not the paper.
- The sandbox recycled once during the run (about 21:21 IST); the AmberTools install was restarted and all files on /workspace survived. No result file was affected.
